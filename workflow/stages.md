# 主线环节索引（兼容性参考）

> 新入口通过 `workflow/workflowctl.py context <id>` 选择 `workflow/stages/S1～S6/SKILL.md`。代理只加载当前阶段 Skill；本文不再是启动必读文件。

每个环节四要素:**职责 / 输入 / 输出 / 完成判据**。产物字段模板统一见 `artifacts.md`。`config/skills.md` 是运行时挂载表，代理只加载当前阶段中状态为“启用”的技能。目标项目注册项(`config/projects.md`)声明的流程扩展仍在**现有环节内部**执行,其完成判据并入所属环节,不新增阶段。每次阶段尝试先运行 `metrics-start`，退出前统一写 `work/<id>/metrics.md`。

## S1 解析与影响面分析

- **职责**:理解 PRD → 判定目标项目(查 `config/projects.md` 的判定规则)→ 调研代码影响面 → 提取验收标准 → 歧义分类(阻塞性/非阻塞)
- **输入**:`prds/<id>.md`
- **输出**:`work/<id>/analysis.md`
- **完成判据**:影响面精确到文件路径;每条验收标准都写了"如何验证";歧义已分类。阻塞性歧义非空 → 触发闸口A
- **纪律**:只读目标仓库,不写。PRD 缺验收标准时,代理反推并标注"AI 反推",在闸口A 一并请人确认

## S2 技术方案

- **职责**:把影响面细化为文件级改动清单;数据变更单列(DDL 草案);每条验收标准映射到验证动作;跨项目需求拆有序子任务;按项目配置确定正式变更文档路径;写 10 行内审批摘要;仅在跨项目、复杂异步链路或人类明确要求分享时按需生成影响面图
- **输入**:analysis.md(+ questions.md 若闸口A发生过)
- **输出**:`work/<id>/plan.md`(含正式变更文档路径；按需附影响面图链接) → 按风险策略决定是否停在闸口 B；R2/R3 必须停，R0/R1 只有项目配置明确允许时可跳过
- **完成判据**:每个改动有仓内既有参照;每条验收标准在验证映射中出现;含"明确不做"清单;影响面图及其审查不参与 S2 或 Gate B 的完成判定
- **纪律**:最小改动原则;方案被人类打回时修订后再次请求批准,修订记录留在 plan.md 末尾

## S3 实现

- **职责**:在目标项目注册分支模型定义的需求分支上按 plan.md 编码,同步写测试和正式变更文档,按逻辑单元 commit(不 push)
- **输入**:plan.md(闸口B 已通过——执行前必须核对 state.md)
- **并发隔离前置**:具备 Shell/Git 且仓库有可用基线时,先在注册仓库中校验目标分支完整名称;注册项声明远端基线时先 `git fetch`,仅声明本地基线时直接解析,两者都必须得到确定 commit。再核验目标路径/分支归属并从该 commit 创建或复用独立 worktree;成功后立即把绝对路径写入项目行。无可用基线或能力不足时,只有任务调度者或人类明确保证注册目录被本需求独占才可串行使用,否则 BLOCKED
- **Git 安全前置检查**(开工前逐项核验,任一不满足即处置如下):
  1. 解析并核对目标项目在项目状态表中的**工作目录**与**目标分支**,git 操作只在该工作目录内执行;有 shell 时用 `git check-ref-format --branch "<目标分支>"` 校验实际完整分支名,失败即 BLOCKED
  2. 检查当前分支与工作区状态(`git status`、`git branch --show-current`)
  3. **存在无法确认属于本需求的未提交修改 → 立即 BLOCKED**,报告给人;**禁止**自动 `stash`/`reset`/`checkout -f`/丢弃任何修改
  4. 新建 worktree 的分支起点必须等于并发隔离前置步骤解析出的基线 commit;恢复既有 worktree 时核对提交集合属于本需求
  5. 项目状态表记录的目标路径/分支与实际不一致时立即 BLOCKED,不擅自复用、覆盖或改签归属
- **输出**:分支上的代码与正式变更文档 + `work/<id>/impl-log.md`(完成项对照表 + 文档提交 + 偏离记录)
- **完成判据**:plan.md 改动清单全部处理;每条偏离已记录并分级
- **纪律**:遵守目标项目注册项中声明的规范文件;**实质性偏离(范围扩大/数据结构变化)必须回闸口B**,细节微调记录即可;不动无关代码

## S4 验证

- **职责**:执行目标项目注册的验证命令 + 验收标准逐条核对 + 正式变更文档检查 + 代理以评审者视角自审完整 diff + 偏离落实核对
- **输入**:分支代码 + analysis.md(标准)+ plan.md(验证映射)
- **输出**:`work/<id>/verify.md`(逐轮追加,节标题含项目名+该项目回修轮次;回修轮次按项目状态表各行独立计数,见 loops.md L1)
- **验证项四态**(每项只能取其一,禁止其他写法):
  - `PASS` 已执行且通过
  - `FAIL` 已执行未通过 → 回 S3(L1 循环)
  - `NOT_RUN` 因环境/权限未执行 → 记录原因,等待人工补跑或人类明确接受风险(原话记入 state.md)
  - `BLOCKED` 无法继续 → 按协议挂起
- **联测子步骤(仅当项目注册启用 `dual-baseline-test`)**:本地验证满足完成判据后,按 `workflow/extensions/dual-baseline-test.md` 执行 dev 联测,联测状态记入 state.md 项目状态表的"联测状态"列。**联测不是独立阶段,主阶段始终为 S4**。
- **完成判据**(进入 S5 的条件):
  - 项目配置 `advisory_verification` 列出的全仓参考性检查不参与流转判定;其余项目注册验证项按四态规则判定
  - 项目配置要求的正式变更文档和集中日志均已存在并与实际改动一致;启用双基线联测时,文档提交已移植到本轮 test 分支并有 hash 证据
  - 所有验证项为 `PASS`,或存在 `NOT_RUN` 但已取得人类明确确认;**`NOT_RUN` 永远不得记为 `PASS`**;存在 `FAIL`/`BLOCKED` 时不得进入 S5
  - 启用联测的项目:还须联测状态为 `PASS`(或 `NOT_RUN` 已获确认),否则 S4 未完成
- **纪律**:结果如实记录;禁止删测试/放宽断言换通过。无 shell 能力时按协议降级(生成命令清单请人执行,人执行前相关项均为 `NOT_RUN`)

## S5 交付

- **职责**:推送分支;创建 MR/PR(或降级为 patch+描述文本);在交付说明中列出正式变更文档;撰写含评审重点提示与部署注意的交付说明
- **输入**:verify.md(满足 S4 完成判据:全 PASS,或 NOT_RUN 已获人类确认且原话在 state.md)
- **开始前 Git 核验**(启用双基线联测时尤为关键):确认当前分支 == 项目状态表“分支”列记录的需求分支、HEAD 指向其最新 commit、工作区干净、提交集合 == 预期。MR/PR 的目标分支取项目注册项“分支模型”声明的交付基线;启用 `dual-baseline-test` 时才固定为需求分支 → master,且绝不在 test 分支或 dev 基线上推送/建 MR
- **输出**:`work/<id>/delivery.md` + 远端分支/MR;更新该项目行为“闸口C=等待中、行状态=等待闸口C”,按 protocol.md 重算顶层状态 → **停在闸口C**
- **完成判据**:分支只含本需求 commit;跨项目需求写明合并顺序
- **纪律**:评审意见回来时立即把目标项目行置为“阶段=S3、行状态=进行中、闸口C=第N轮评审回流”,按 protocol.md 聚合规则重算顶层状态,再执行 S3→S4→更新交付物并把轮次记入 delivery.md

## S6 完成归档

- **职责**:所有项目通过闸口C 后,state.md 顶层状态置为 `完成`;把本需求中沉淀的可复用经验(新的参照实现、踩过的坑)按 `config/skills.md` 的沉淀协议写成技能候选
- **输入**:项目状态表**所有行**的闸口C 均为"已合并"或"已验收(无MR)"(patch 降级交付由人验收 → "已验收(无MR)")。**任一行未达此状态,不得进入 S6**——单个项目合并不提前完成整个需求
- **输出**:state.md(所有行状态=`已完成`,顶层状态=`完成`)+ 可选的 `skills/candidates/` 条目
- **联测分支清理子步骤(仅当项目启用 `dual-baseline-test`)**:清理依据是 **verify.md 的"联测分支历史"完整列表**(唯一数据源,而非 state.md"联测分支"列——后者只显示当前最新一轮,不足以全量清理)。先按精确分支名去重,再逐个核名后删本地/远端,每个分支分别记录本地与远端清理结果;详见 `workflow/extensions/dual-baseline-test.md` 清理规则
- **临时 worktree 清理子步骤(仅当为并行建过 worktree)**:
  1. 只处理 state.md 交接备注明确标记为"本工作流创建"的临时 worktree,不碰主工作树与用户自有 worktree
  2. 先用 `git worktree list --porcelain` 定位**主工作树**与目标临时 worktree 的精确绝对路径
  3. 清理前核验:执行 `git status --porcelain --ignored`;只有命令退出码为 0、输出为空、分支已交付且该行闸口C 已完成才可自动删除。任何命令失败或 tracked/untracked/ignored 文件都会阻断自动清理,记"待人工处理",防止 `git worktree remove` 连同被忽略文件一起永久删除
  4. **把命令执行目录切到目标 worktree 之外**(如主工作树;Windows 上以目标 worktree 为当前目录直接删会失败),再 `git worktree remove <目标绝对路径>`
  5. 找不到安全的执行目录、或工作区不干净 → 只记"待人工处理",不强删;删除失败的原因与待人工动作写入 delivery.md
- **完成判据**:state.md 顶层状态=`完成`(已完成的需求不再被断点恢复逻辑推进);work/<id>/ 齐全即为归档,不删除;启用联测的项目其 test 分支(按 verify.md 历史列表)、并行创建的 worktree 状态均明确为"已删除"或"待人工处理"
