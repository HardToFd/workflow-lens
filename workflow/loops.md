# 循环流程(所有回路的次数限制与升级规则)

主线是单向的,循环只发生在四个明确定义的回路上。**每个回路都有轮次上限和升级出口,防止代理无限自转。**

## L1 回修循环(S4 ⇄ S3)

- **触发**:验证矩阵出现 `FAIL`(四态定义见 stages.md S4;`NOT_RUN` 不触发回修,走人工补跑/风险确认,`BLOCKED` 直接挂起)
- **动作**:回 S3 在同分支追加 commit 修复 → 重跑**整个**验证矩阵(不是只重跑失败项——修复可能弄坏别处)
- **上限**:每个项目 3 轮(可在此文件调整),**按项目状态表各行"回修轮次"列独立计数**——跨项目需求中项目 A 的轮次不累加到项目 B
- **升级**:某项目行第 3 轮仍有 `FAIL` → 只把**该行**置 BLOCKED,verify.md 写明卡点、已尝试的修法、代理的判断(疑似方案问题?环境问题?),等人处置;其他项目行不受影响
- **不计入 L1 的情况**:闸口C 评审回流(L2)导致的回 S3、重建 test 分支等动作**只计 L2**;仅当其后的 S4 重验真出现 `FAIL` 才为该项目 +1 L1 轮次
- **度量**:离开失败的 S4 前写一条 `metrics.md`，下一次 S3 的 `rework-count` 加 1；同一失败不得在 S3、S4 两边重复计数
- **禁止**:通过删测试、注释断言、跳过检查来"通过"

## L2 评审回流(闸口C ⇄ S3)

- **触发**:人类在闸口C 提出评审意见
- **动作**:意见按条编号记入 delivery.md → 回 S3 修复 → S4 重验(可只跑受影响项+全量静态检查)→ 更新交付物 → 回到闸口C
- **轮次归属**:评审回流只增加 delivery.md 的 L2 轮次,**不增加项目行"回修轮次"(L1)**;重建 test 分支等动作本身也不计 L1(见 L1 的"不计入"条)
- **上限**:无硬上限(评审多少轮由人决定),但**同一条意见修 2 次仍不满意**时,代理应请求人类给出更具体的期望而不是继续盲试
- **记录**:每轮在 delivery.md 追加"第 N 轮评审回流"小节
- **度量**:离开 S5 前记录本轮，下一次 S3 的 `rework-count` 加 1，并在备注引用对应评审意见编号

## L3 方案修订循环(闸口B ⇄ S2)

- **触发**:人类打回 plan.md
- **动作**:按意见修订 → plan.md 末尾记录修订说明 → 再次请求批准
- **上限**:3 轮后仍无法达成一致 → 大概率是 S1 理解就错了,回 S1 重做解析(此时旧 analysis.md 改名留档 analysis-v1.md)
- **度量**:每次 Gate B 打回都先结束当前 S2 记录，下一次 S2 的 `rework-count` 加 1；退回 S1 时同样结束 S2，再由新 S1 尝试单独计时

## L4 需求级循环(S6 → 新需求)

- **触发**:S6 归档时发现 PRD 只完成了一部分(PRD 过大被拆),或评审中砍掉的范围要另立需求
- **动作**:不复用旧 id。拆出的部分作为新 PRD 进 `prds/`,走全新流水线;新 PRD 的"补充信息"注明来源需求 id,S1 可复用旧 analysis 的调研结论
- **原则**:一个 id 一条主线一次交付,禁止在已交付的 id 上追加范围("顺便再加个功能"=新需求)

## 全局熔断

以下情况无条件转 BLOCKED 等人,不进任何循环:
- 发现 PRD 与目标仓库现状根本冲突(功能已存在/依赖的模块已下线)
- 验证暴露出改动之外的**存量**严重问题(数据错误、安全漏洞)——记录并上报,不擅自扩大修复范围
- 任何环节需要生产环境操作(执行 DDL、改线上配置)——本工作流权限止步于代码与 MR
