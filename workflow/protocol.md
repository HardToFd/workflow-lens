# 核心协议（兼容性深层参考）

> 代理不应在启动时预加载本文。`workflow/manifest.json` 是状态、风险、闸口和路由的机器权威定义；当前阶段行为由 `workflow/stages/Sx/SKILL.md` 定义。本文保留旧版 `state.md`、跨项目聚合和能力降级的详细说明，只有处理相应边界时按需读取。

## 1. 设计原则

- **可移植文件协议**:工作流由 Markdown 任务产物、JSON 机器清单和文件系统状态组成，不依赖平台插件或远端 API。`workflowctl.py` 是无第三方依赖的确定性路由器；无法执行时可由人工读取同一清单和阶段 Skill 中继。
- **状态外置**:代理的记忆不可靠(会话会断、上下文会满),一切进度以 `work/<id>/state.md` 为准。**代理随时可被替换,新代理读 state.md 即可无损接管。**
- **产物即接口**:环节之间只通过产物文件交接(见 artifacts.md)。上游环节由谁(哪个模型/哪个人)完成,下游不关心。
- **人类边界按风险执行**:闸口 C 永远存在；闸口 B 对 R2/R3 必经，R0/R1 只有项目配置明确允许时才可跳过。

## 2. 状态机

```
S1 解析 → [闸口A?] → S2 方案 → 闸口B → S3 实现 → S4 验证 ⇄ S3(回修循环) → S5 交付 → 闸口C ⇄ S3(评审回流) → S6 完成
闸口B 打回 → S2 修订;L3 达上限 → S1 重做解析
任何状态可 → 挂起(BLOCKED, 原因写入 state.md)
```

- 环节定义以 `workflow/stages/Sx/SKILL.md` 为准；`workflow/stages.md` 仅为旧入口兼容索引
- 合法转移只有上图所示;跳环节(如没有 plan.md 就写码)是协议违规
- 回修循环与评审回流的次数限制见 `workflow/loops.md`
- 部分项目在 S4 内部含"联测"子步骤(见 `workflow/extensions/`),它不是独立阶段,主阶段始终为 S4

**并发规则**:`work/<id>/` 只隔离过程产物,**不隔离代码工作区**——同一 git 工作目录同时只能检出一个分支。
- 具备 Shell/Git 且目标仓库有可用基线时,**每个需求进入 S3 前默认使用独立 git worktree**,无需逐次请求人类同意。创建前必须在注册仓库中依次完成目标分支完整校验、把注册项声明的基线解析为确定 commit;声明远端基线时须先 `git fetch`,仅声明本地基线时不要求远端。任一步失败即 BLOCKED。
- 默认路径为目标仓库同级的 `<仓库名>-worktrees/<需求id>`。仅当目标路径/分支尚未占用时从上述确定 commit 创建;已存在时只有 state.md 明确记录属于本需求才可核验复用,否则 BLOCKED。
- worktree 创建或复用成功后,立即把绝对路径写入 state.md 项目状态表,并在交接备注标注"临时 worktree(本工作流创建)"以便 S6 清理。
- 无 Shell/Git 或仓库没有可用基线时,只有任务调度者或人类明确保证该注册目录被本需求独占才可串行使用;扫描其他 `work/*/state.md` 只是诊断,不能提供互斥保证。无法取得独占保证则 BLOCKED。不要用 Markdown 文件模拟并发锁。
- 不同目标仓库的需求工作目录天然隔离,可并行。

**单环节入口前置检查**:经平台快捷命令(或人工指定"只跑 Sx")进入单个环节前,必须核验以下条件,任一不满足即拒绝执行并说明缺少的前置条件:
1. 转移合法性,满足下列之一即可:
   - **首次启动例外**:目标为 S1、`prds/<id>.md` 存在且 `state.md` 不存在 → 允许,先初始化 state.md 再执行
   - **同环节恢复例外**:目标阶段 == state.md 当前阶段,且状态为"进行中"或 BLOCKED 已解除 → 允许断点恢复,不视为跳环节
   - **正常转移**:state.md 存在,且从当前阶段转移到 Sx 是状态机声明的合法转移
2. Sx 的输入产物齐全(见 stages.md 各环节"输入")
3. Sx 之前的必经闸口已在 state.md 留有批准记录
4. **跨项目需求**:动作以项目状态表中的**目标行**为判断依据(见 §3.1),不以顶层"环节"字段为准

## 3. state.md — 唯一进度真相

需求 id 用于文件路径、目录名和 git 分支名,创建 `prds/<id>.md` / `work/<id>/` / 分支前必须先校验,不合法则拒绝并请用户改名(**不自动清洗**,以免产生不可追溯的新 id):

```
合法 id 正则:^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$
额外禁止:包含 ..、路径分隔符(/ \)、空格;以 . 或 - 结尾
跨平台禁止:id 以 .lock 结尾(不区分大小写);id 第一个 . 前的主名为 CON/PRN/AUX/NUL/COM1~9/LPT1~9(不区分大小写)
```

项目确定后还必须校验**实际完整分支名**:有 shell 时执行 `git check-ref-format --branch "<分支名>"`;无 shell 时由人类中继执行。校验失败即 BLOCKED,不得仅凭 id 正则断言分支名合法。

**首次初始化**:`state.md` 不存在且进入 S1 时,先写顶层 `环节: S1`、`状态: 进行中`、`闸口A: 未到`、`闸口B: 未到`、`NOT_RUN 确认: 无`;项目状态表暂时只保留表头。S1 判定目标项目后、完成 S1 或进入闸口A前,必须补齐所有项目行。下方是项目行已确定后的常规格式。

```markdown
# state: <需求id>
- 环节: S3                      # 顶层摘要,取项目状态表各行最靠前阶段(S1<S2<S3<S4<S5<S6);跨项目命令不以此为唯一判断依据
- 状态: 进行中 | 等待闸口 | BLOCKED(原因) | 完成    # 顶层摘要,按下方聚合规则计算
- 闸口A: 未到 | 等待中 | 跳过 | 已通过 <日期>(答复见 questions.md)
- 闸口B: 未到 | 等待中 | 已通过 <日期>("<人类原话>")     # 需求级:一次批准覆盖全需求(含所有项目)
- NOT_RUN 确认: 无 | <日期>("<人类原话>",涉及项见 verify.md)

## 项目状态表(单项目也用一行,单/跨项目统一格式)
| 项目 | 工作目录 | 分支 | 联测分支 | 联测状态 | 阶段 | 回修轮次 | MR/PR | 闸口C | 行状态 |
|------|----------|------|----------|----------|------|----------|-------|-------|--------|
| <注册名> | <注册路径或worktree路径> | <项目注册的需求分支> | - | - | S3 | 0 | 未创建 | 未到 | 进行中 |

- 交接备注: <给下一个接管者(可能是另一个模型)的必要上下文,保持精简>
```

- **联测分支 / 联测状态**两列仅对启用 `dual-baseline-test` 的项目有效,其余填 `-`。联测状态枚举:`NOT_STARTED | RUNNING | PASS | FAIL | NOT_RUN | BLOCKED`。
- **回修轮次列**:每个项目独立计数,只用于该项目行的 L1 熔断判断(见 loops.md);**顶层无回修轮次字段**,跨项目各行互不合并。
- **闸口 B 是需求级**(顶层单字段),闸口 C 是**项目级**(项目状态表每行一列)——跨项目需求方案一次批准,但每个项目的 MR 各自评审、各自合并。
- **闸口C 列枚举**:`未到 | 等待中 | 第N轮评审回流 | 已合并 | 已验收(无MR)`。其中"已验收(无MR)"用于 patch 降级交付(无远端合并动作,由人验收结束)。
- **行状态枚举**:`进行中 | 等待闸口C | BLOCKED | 已完成`。行状态=已完成 要求该行闸口C ∈ {已合并, 已验收(无MR)}。
- **BLOCKED 同步规则**:项目内任一步骤写“BLOCKED/挂起”时,保留该行当前阶段并把**目标项目行状态**同步置 `BLOCKED`;若该步骤有验证项、联测状态等子状态,也同步置 `BLOCKED`,随后按下方规则重算顶层状态。阻塞经人确认解除后,把行状态恢复为 `进行中`,再按同阶段恢复规则续跑并重算顶层状态。项目表尚未建立时才直接把顶层状态置 `BLOCKED`。
- **顶层状态聚合规则**(按顺序取第一条命中,保证任意行组合都有唯一顶层状态):
  1. 全部项目行=已完成 → 顶层 `完成`
  2. 存在可执行项目行(非已完成、非 BLOCKED、非等待闸口C)→ 顶层 `进行中`
  3. 无可执行行,且所有未完成行都在等待闸口C → 顶层 `等待闸口`
  4. 无可执行行,且至少一个必需项目行为 BLOCKED(含"等待闸口C + BLOCKED"混合)→ 顶层 `BLOCKED`,交接备注列出阻塞项目与仍可由人完成的闸口动作
- S1 尚未判定项目、项目表为空时不套用上述行聚合规则,使用首次初始化状态;触发闸口A时把顶层状态和闸口A分别置为 `等待闸口`、`等待中`。
- **进入 S6 的条件**:项目状态表**所有行**的闸口C 都为"已合并"或"已验收(无MR)"。单个项目合并**不得**提前把整个需求标记完成。

### 3.1 跨项目动作规则(单环节命令与断点恢复的唯一依据)

1. 每次执行动作(S3/S4/S5 等)都以项目状态表中的**目标行**为准,不看顶层"环节"字段。
2. 单环节命令在跨项目需求中,若不指定项目名,则只处理"当前最靠前且满足该环节前置条件"的那一行,并在回复中明确报告本次操作的目标项目;要操作其他行须显式指定项目名。
3. 已完成某环节的项目行不得被重复实现/验证/交付——恢复时先读其阶段字段判断。

**写入纪律**:每完成一个环节、每通过一个闸口、每次进入等待,立即更新。人类的批准必须记录日期与原话——这是断点续跑时判断"闸口是否已过"的唯一依据,防止重复问或漏问。

## 4. 闸口协议

| 闸口 | 时机 | 触发条件 | 人类动作 | 通过判据 |
|------|------|----------|----------|----------|
| A | S1后 | analysis.md 存在阻塞性歧义(不同理解→不同实现) | 回答选择题 | 答复写入 questions.md |
| B | S2后 | 风险为 R2/R3，或项目策略要求 | 审 plan.md 摘要 | 明确同意的表述("同意/OK/继续/approved") |
| C | S5后 | **永远触发** | 评审交付物 | 明确的合并/验收确认 |

在闸口停下时,代理必须:说明停在哪个闸口、人类需要做什么、什么样的回复算通过。**沉默、含糊表述("嗯""看看再说")不算通过。**

## 5. 能力降级(平台无关的关键)

代理能力不同,协议通过降级保持可运行——**降级改变"谁执行动作",不改变"环节顺序与产物要求"**:

| 能力缺失 | 降级方式 |
|----------|----------|
| 不能执行 shell(如网页版对话) | 所有阶段的 Shell/Git 命令均由代理生成清单,人类执行后贴回输出;包括 S3 worktree/分支/提交和 S5 push/MR,不只是 S4 验证 |
| 不能直接读写文件 | 人类充当文件系统:代理输出产物全文,人类保存;人类粘贴 state.md 给代理恢复上下文 |
| 无子代理/并行能力 | S1 影响面调研串行做,多花时间,产物要求不变 |
| 上下文窗口小 | 依赖 state.md 交接备注 + 各产物文件的"摘要"节,分多会话完成单环节 |
| 无网络/无 MR 权限 | S5 降级为:产出 patch 文件 + MR 描述文本,人类手工提交 |

详细的能力自检清单见 `config/capabilities.md`。

## 6. 扩展点(本协议的五个可插拔面)

> `config/capabilities.md` 是**运行环境配置**(描述当前代理能力档位),不是扩展面,不计入下列五项。

1. **项目注册**(`config/projects.md`):新增目标仓库=加一条注册项,主线流程零改动
2. **技能挂载**(`skills/` + `config/skills.md`):按阶段读取挂载表中状态为“启用”的技能；外部 Agent Skill 通过工作区适配器挂载，表格行序就是同阶段执行顺序
3. **流程扩展**(`workflow/extensions/`):在**现有环节内部**插入子步骤(如 S4 内的双基线联测),由 `config/projects.md` 注册项按项目声明启用;可以增加子步骤、可选的项目状态表列与产物小节,**严禁**新增顶层阶段、新增闸口、改变状态机转移、或改动产物必填字段。子步骤的完成判据并入其所属环节(如联测未过则 S4 不算完成)。
4. **循环策略**(`workflow/loops.md`):回修次数、升级阈值可按团队调整
5. **产物模板**(`workflow/artifacts.md`):字段可增,**不可删必填字段**
